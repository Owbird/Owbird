# I Looked Up 1.4 Million IP Addresses. Here's What Showed Up.

I took a sneak peek into Ghana's internet infrastructure and found 1.4 Million IP addresses.

## First, Find Ghana's Internet

There is no convenient `ghana.internet` file containing everything we need.

I started with [Autonomous System Numbers, or ASNs](https://en.wikipedia.org/wiki/Autonomous_system_(Internet)).

An autonomous system is a network run by an organisation such as an internet provider, university or company. Its ASN is a unique identifier, written with an `AS` prefix followed by digits. For example, AS30986 belongs to Scancom Limited, MTN Ghana.

Those networks announce IP prefixes, which describe blocks of addresses they can route traffic to.

## 1. Find ASNs associated with Ghana.
I found registered Ghanaian ASNs using [RIPEstat](https://stat.ripe.net/). There were 94 ASNs.

```python
url = "https://stat.ripe.net/data/country-resource-list/data.json"

response = requests.get(url, params={"resource": "gh"}, timeout=30)
```

## 2. Find each ASNs IPv4 range.
RIPEstat also returns IPv4 prefixes such as `41.189.160.0/24`. Expanding all the ranges for each prefix gave me 1,468,160 IPs.

## 3. Look up the resulting addresses.
I looked up the addresses using [Shodan's InternetDB](https://internetdb.shodan.io/). It provides existing observations about an IP address, including:

- Reported open ports
- Hostnames
- Software identifiers
- Classification tags
- Vulnerability identifiers

These results came from an existing measurement source. I did not independently verify that every reported service was still reachable at the time of the lookup.

## Making It Survive Its Own Ambition

An individual lookup was easy. Running the full collection meant keeping track of progress and recovering when something stopped.

The collection needed to remember which addresses had been processed, distinguish an empty result from a failed request, and retry temporary failures.

Increasing concurrency ran into rate limits: the server would respond with HTTP 429, telling the collector to wait.

The system grew into distributed workers sharing a Neon Postgres database. Work was split into jobs, with leases so a worker could claim a batch without another worker processing the same job at the same time.

The database tracked observations, retries, worker heartbeats and pacing.

If a worker disappeared, the work could become available again after its lease expired.

The goal was to keep making progress without needing to restart the whole thing whenever one machine had other plans.

## What Came Back

At the end of the run, the results were:

| Lookup outcome | Addresses |
|---|---:|
| InternetDB record returned | **25,006** |
| No data returned | **1,443,136** |
| Retry pending | **5** |
| Retry attempts exhausted | **13** |
| **Total** | **1,468,160** |

About 1.7% of the address pool returned records.

The other 98.3% cannot be treated as empty. "No data" means the source returned no record. It does not establish that the address was unused, that no device existed, or that whatever was there was secure.

## The Ports Were Interesting

Among the 25,006 addresses with records, these were the most frequently reported ports:

| Port | Addresses reporting it |
|---|---:|
| 161 | **7,467** |
| 7547 | **6,900** |
| 80 | **4,236** |
| 443 | **3,453** |
| 22 | **3,377** |
| 2000 | **2,063** |
| 179 | **1,872** |
| 123 | **1,460** |
| 8291 | **1,445** |
| 53 | **839** |

Ports 161 and 7547 each appeared on more addresses than either 80 or 443. That made me wonder which networks contributed those observations, and how much of the visible picture came from network infrastructure compared with conventional web hosting.

The next step is to break the distribution down by network and examine the accompanying metadata.

A port number alone does not prove which application is running, how it is configured, or whether it is vulnerable.

Also, these counts overlap. One address can report several ports, so adding the rows together would not give us a device count.

## There Was More Than a Port List

Of the addresses with records:

- 3,896 included at least one hostname.
- 5,924 included at least one software identifier.

InternetDB also supplied tags. These included 670 addresses tagged `eol-product` and 134 tagged `eol-os`.

These tags give me leads to investigate, though confirming vulnerabilities on those machines would require a separate investigation.

## What the Atlas Is Becoming

With the results organised this way, I can compare reported services across networks and examine where InternetDB has records and where it does not. Repeating the collection would let me track changes in the observations. I can also make the information easier to explore than a collection of API responses.

I'm building the Ghana Internet Atlas to investigate the networks associated with Ghana, with the source and collection date visible alongside the limits of each observation.

I also built an explorer where you can look through the networks and observations yourself: [https://ghana-internet-atlas.vercel.app](https://ghana-internet-atlas.vercel.app)
